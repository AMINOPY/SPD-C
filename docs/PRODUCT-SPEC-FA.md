# مشخصات محصول Spd con

این سند مرجع محصول است: برنامهٔ اصلی اندروید باید برای کاربر عادی ساده باشد و کارهای روزمرهٔ ساخت کانفیگ و مدیریت کاربران/نودها تا حد ممکن از داخل اپ انجام شود. پنل وب جداگانه جزو نیازمندی‌های نسخهٔ اول نیست.

## 1) تجربهٔ کاربری نهایی

### صفحهٔ اصلی
- کارت‌های واضح: «ساخت کانفیگ»، «کانفیگ‌های من»، «کاربران»، «نودها» و «وضعیت سرویس».
- فرم ساخت کانفیگ کوتاه؛ تنظیمات تخصصی به‌صورت بسته در «تنظیمات تکمیلی».
- دکمه‌های واضح برای ساخت، کپی، QR، اشتراک‌گذاری، ذخیره و آزمایش کانفیگ.
- متن خطا باید بگوید چه چیزی اشتباه است و قدم بعدی چیست؛ از نمایش JSON خام به کاربر عادی خودداری شود.

### ساخت سریع کانفیگ
ورودی‌های اصلی: نام کانفیگ، نود، پروتکل، SNI (در صورت نیاز) و در صورت لزوم اطلاعات احراز هویت صادرشده از نود. UUID نباید در فرم عادی دیده یا دستی وارد شود؛ برای پروتکل‌هایی که UUID لازم دارند، برنامه آن را خودکار تولید کند یا از سرور بگیرد.

- انتقال: حالت «خودکار / پیشنهاد هوشمند» پیش‌فرض باشد. برنامه نوع اتصال دستگاه (Wi-Fi/دادهٔ همراه) را تشخیص می‌دهد و فقط یک پیشنهاد اولیه می‌دهد؛ انتخاب انتقال نهایی باید با قابلیت‌های واقعی نود و تست اتصال تأیید شود.
- Fragment و پروفایل شبکه: به‌صورت پیشنهادهای اختیاری و سازگار با نوع کانفیگ ارائه شوند؛ روی پروتکل‌هایی که پشتیبانی نمی‌کنند پنهان باشند. ادعای تشخیص قطعی DPI بدون تست واقعی ممنوع است.
- REALITY ساده: کاربر SNI را وارد می‌کند. برنامه فقط وقتی نود REALITY واقعی انتخاب شده، کلید عمومی، short ID و سایر پارامترهای معتبر را از پیکربندی نود می‌گیرد. SNI به‌تنهایی برای ساخت کانفیگ REALITY معتبر کافی نیست؛ پارامترهای رمزنگاری نباید حدس زده شوند.
- نام‌هایی مانند digikala.com صرفاً ورودی کاربر هستند و نباید بدون مجوز/پیکربندی واقعی به‌عنوان مقصد قابل‌استفاده یا دامنهٔ سرور تأیید شوند.
- VLESS، VMess، Trojan، Shadowsocks، Hysteria2 و TUIC فقط زمانی «آمادهٔ اتصال» معرفی شوند که سازنده، خروجی و کلاینت/هستهٔ مربوطه واقعاً از آن‌ها پشتیبانی کند.

### مدیریت
- کاربر: ساخت، فعال/غیرفعال، تاریخ انقضا، سهمیهٔ حجم، مصرف، تعداد اتصال مجاز، یادداشت و ریست مصرف با ثبت رویداد مدیریتی.
- نود: افزودن، ویرایش، تست سلامت، نسخهٔ هسته، پروتکل‌های پشتیبانی‌شده و وضعیت آخرین گزارش.
- دسترسی مدیر باید سمت API کنترل شود؛ پنهان کردن دکمه در اپ به‌تنهایی مجوز امنیتی نیست.

## 2) معماری

1. **Android app (Kotlin + Jetpack Compose):** رابط فارسی ساده، سازنده/اعتبارسنج کانفیگ، QR و clipboard، ذخیرهٔ محلی رمزنگاری‌شده، و کلاینت API.
2. **Cloudflare Worker:** API احراز هویت و مدیریت؛ اعتبارسنجی ورودی، نقش‌ها، محدودسازی درخواست، ثبت audit log و هماهنگی با نودها.
3. **Cloudflare D1:** کاربران، نودها، کانفیگ‌ها/اشتراک‌ها، سهمیه‌ها، مصرف و رویدادهای مدیریتی.
4. **Cloudflare KV:** تنظیمات غیرحساس، فلگ‌ها و cache کوتاه‌عمر؛ نه محل نگهداری رمزها یا دادهٔ تراکنشی اصلی.
5. **Cloudflare R2 (اختیاری):** نسخهٔ پشتیبان رمزنگاری‌شده و فایل‌های خروجی/گزارش در صورت نیاز.
6. **Node agent روی VPS مدیریت‌شده:** اتصال امن و احراز هویت‌شده به API؛ خواندن آمار Xray، سلامت سرویس و اعمال سیاست‌های پشتیبانی‌شده.
7. **Xray-core و هسته‌های دیگر:** روی سرور/نود اجرا می‌شوند، نه داخل Cloudflare Worker. Worker جایگزین سرور VPN یا تونل شبکه نیست.

Cloudflare می‌تواند بک‌اند و مدیریت را میزبانی کند؛ برای اتصال واقعی VPN و اجرای Xray/Hysteria2/TUIC به نود واقعی نیاز است. داشتن پنل وب مستقل الزامی نیست.

## 3) ساختار سورس هدف

```text
android/
  app/src/main/java/com/spdcon/app/
    ui/                 # صفحه‌ها و اجزای Compose
    config/             # مدل، parser، generator و validator
    data/local/         # پایگاه داده و ذخیرهٔ رمزنگاری‌شده
    data/remote/        # API و مدل‌های شبکه
    nodes/              # مدیریت نود و تست سلامت
    users/              # مدیریت کاربران و سهمیه
    security/           # توکن و رمزنگاری
backend/                # API توسعه/سازگاری و تست‌ها
cloudflare/
  worker/               # API قابل استقرار روی Cloudflare
  migrations/           # طرح D1 و مهاجرت‌ها
node-agent/             # عامل نود و هماهنگ‌کنندهٔ آمار هسته
deploy/
  docker-compose.yml    # فقط سرویس‌های قابل اجرا روی VPS؛ نه اجرای VPN داخل Worker
docs/
  PRODUCT-SPEC-FA.md
  API.md
  DATA-MODEL.md
  CORE-STATUS.md
```

ساختار فعلی را مرحله‌به‌مرحله به این هدف نزدیک کنید؛ انتقال یک‌بارهٔ همهٔ فایل‌ها بدون تست توصیه نمی‌شود.

## 4) مدل دادهٔ اصلی

- `users`: `id`, `username`, `password_hash` یا شناسهٔ هویت خارجی، `role`, `enabled`, `expires_at`, `quota_bytes`, `used_bytes`, `max_connections`, `created_at`.
- `nodes`: `id`, `name`, `region`, `api_secret_hash`, `enabled`, `last_seen_at`, `core_type`, `core_version`, `capabilities_json`.
- `profiles`: `id`, `owner_user_id`, `node_id`, `protocol`, `name`, `config_encrypted`, `created_at`, `updated_at`.
- `subscriptions`: `id`, `user_id`, `token_hash`, `enabled`, `expires_at`, `created_at`.
- `usage_counters`: `node_id`, `user_id`, `source`, `upload_bytes`, `download_bytes`, `last_event_id`, `updated_at`; کلید یکتا روی `(node_id,user_id,source)`.
- `usage_events`: `id`, `node_id`, `user_id`, `event_id`, `upload_delta`, `download_delta`, `created_at`; `event_id` برای idempotency.
- `sessions`: شناسهٔ نشست، کاربر، نود، زمان شروع/پایان و وضعیت؛ فقط در صورت وجود منبع معتبر برای هم‌بستگی.
- `audit_logs`: مدیر، عمل، هدف، زمان و فرادادهٔ غیرحساس.

در D1 از foreign key و index برای username، node_id، user_id و زمان رویداد استفاده شود. کلیدها و توکن‌های خام نباید در log یا جدول عمومی ذخیره شوند.

## 5) APIهای هدف

تمام مسیرهای مدیریتی نیازمند احراز هویت و نقش مناسب‌اند؛ گزارش نودها باید با secret مستقل هر نود و ترجیحاً امضای درخواست/زمان و جلوگیری از replay محافظت شود.

- `POST /v1/auth/login`, `POST /v1/auth/refresh`, `POST /v1/auth/logout`
- `GET/POST /v1/users`, `GET/PATCH /v1/users/{id}`, `POST /v1/users/{id}/reset-usage`
- `GET/POST /v1/nodes`, `GET/PATCH /v1/nodes/{id}`, `POST /v1/nodes/{id}/health-check`
- `POST /v1/profiles/validate`, `POST /v1/profiles/generate`, `GET/POST /v1/profiles`, `DELETE /v1/profiles/{id}`
- `GET /v1/subscriptions/{token}` (توکن باید امن و قابل‌لغو باشد)
- `POST /v1/nodes/{id}/usage/report`, `POST /v1/nodes/{id}/heartbeat`
- `GET /v1/admin/overview`, `GET /v1/admin/audit-logs`

هر API باید schema، کنترل اندازهٔ ورودی، خطای قابل‌فهم و تست داشته باشد. نام‌های این بخش قرارداد هدف‌اند؛ پیش از استفاده در کلاینت باید با مسیرهای واقعی و نسخه‌بندی‌شده هماهنگ شوند.

## 6) Docker Compose و استقرار

- Cloudflare Worker و D1 با Wrangler و migration مستقر می‌شوند و لزوماً در Docker اجرا نمی‌شوند.
- Docker Compose برای سرویس‌های VPS مانند node-agent، Xray-core و سرویس‌های مشاهده‌پذیری استفاده می‌شود؛ پورت‌های مدیریتی نباید عمومی شوند.
- secretها فقط از محیط امن یا secret manager تزریق شوند؛ فایل `.env` واقعی و حاوی secret commit نشود.
- نمونهٔ Compose باید placeholderهای مستند داشته باشد، healthcheck، restart policy، شبکهٔ داخلی و volumeهای پایدار داشته باشد. هیچ endpoint یا رمز پیش‌فرضی نباید به‌عنوان امن فرض شود.

## 7) مراحل پیاده‌سازی و معیار پذیرش

1. **پایه و UI ساده:** فرم کوتاه، صفحهٔ اصلی، ذخیره/کپی/QR، پیام‌های خطای فارسی؛ تست UI و build APK.
2. **درستی سازنده:** round-trip parser/generator برای پروتکل‌های پشتیبانی‌شده، fixtureهای معتبر و بررسی با نسخهٔ pinشدهٔ هسته.
3. **Cloudflare API:** D1 migrations، ورود امن، نقش‌ها، CRUD کاربر/نود و audit logs؛ تست Worker و migration.
4. **اتصال نود:** heartbeat احراز هویت‌شده، health checks و گزارش نسخه/قابلیت هسته.
5. **مصرف و سیاست‌ها:** گزارش مصرف idempotent، سهمیه/انقضا و هشدار؛ enforcement فقط پس از پیاده‌سازی و تست واقعی لغو/قطع نشست در core.
6. **اتصال زنده:** پیاده‌سازی و ممیزی چرخهٔ VPN اندروید یا اتصال به کلاینت/هستهٔ سازگار؛ تست روی دستگاه و نود آزمایشی.
7. **پروتکل‌های اضافه:** Hysteria2/TUIC/Backhaul فقط با runtime واقعی، health check و تست end-to-end؛ generator تنها کافی نیست.
8. **انتشار:** build امضاشده، تست نصب/ارتقا، تهیهٔ نسخهٔ پشتیبان، مستندات بازیابی و بررسی امنیت.

نسخه فقط زمانی «کامل» اعلام شود که build و تست‌ها موفق باشند و قابلیت‌های ادعاشده روی نود آزمایشی واقعی آزموده شده باشند.
